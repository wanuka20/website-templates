# v0.5.6 Gym Migration Risk Register

## How to use this register

The role in the **Owner** column is accountable for the risk during the
Gym-first migration. Before a real pilot, the platform administrator assigns a
named person to each role and records the assignment with the release evidence.
A launch gate is pass/fail: a risk may not be waived by simply accepting a
warning in the browser or deployment log.

| ID | Risk | Owner | Prevention | Detection | Response and rollback | Launch gate |
| --- | --- | --- | --- | --- | --- | --- |
| R-01 | Gym Sheet data is lost, transformed incorrectly, or partially imported | Migration lead | Immutable Sheet backup with checksum; dry-run, idempotent importer; field/image/lead-count mapping | Import report shows missing/changed/rejected fields or counts differ from source | Stop cutover; retain Sheets as source; fix mapping; rerun dry-run; restore database staging backup if it was mutated | One Gym import has zero unexplained required-field, image, or lead-count differences; a staging restore passes |
| R-02 | One site reads or writes another site's content, leads, assets, or revisions | Application engineer | Non-null `site_id`, foreign keys, scoped unique constraints, server data-access layer, least-privilege/RLS policy where selected | Two-site integration tests, database-policy tests, and audit events show mismatched `site_id`/hostname | Suspend affected site; stop writes; invalidate affected cache tags; preserve logs; repair data; rotate credentials if exposure is possible; notify/assess with customer | Seeded site A and B cannot read, create, update, delete, upload, or receive each other's data using guessed IDs or swapped hosts |
| R-03 | Shared cache returns site A content, metadata, or image references to site B | Application engineer | Cache keys/tags include `site_id` and published revision; hostname resolver precedes fetch; no template-only content cache | Warm/cold cache tests across two hostnames after publish, rollback, suspension, and asset replacement | Suspend affected site if public; invalidate the affected site namespaces and paths; fix cache key; rerun cross-host test before re-enable | All cache tests prove response body, metadata, images, and cache activity remain site-scoped |
| R-04 | A public lead is delivered to the wrong customer, dropped, or reported successful falsely | Application engineer | Same server-side hostname resolver for render and lead route; derived `site_id`; validation, honeypot, durable rate limit, delivery status | Route tests, safe delivery-failure logs, site-scoped lead count checks, customer report | Mark delivery failure; retry only through an approved idempotent job; do not expose lead text in logs; fix mapping and run no-real-lead regression | Test leads/fixtures prove correct derived site, rejection for unknown host, truthful failure, and no cross-site lead read |
| R-05 | Domain points to the wrong site, is claimed without verification, or remains public after cancellation | Platform administrator | Globally unique normalized host; requested/pending/verified/active states; manual Vercel verification checklist; domain removal on suspension/cancellation | Domain-state audit, Vercel/DNS check, duplicate-host test, hostname resolver test | Disable domain record first; return safe not-found; remove project domain through approved workflow; invalidate resolution cache | Active custom domain, platform subdomain, unknown, duplicate, pending, failed, suspended, and removed-host cases pass |
| R-06 | Provider outage, database failure, or accidental deletion exceeds recovery capability | Platform operations owner | Daily managed backups, weekly encrypted logical export, asset manifest, four-hour recovery rehearsal, no untested in-place restore | Backup-age check, provider status alert, restore-rehearsal report, failed health/data-access checks | Suspend affected site; restore into non-production first; validate counts/isolation/assets; approve production recovery; record actual RPO/RTO | Restore rehearsal meets the pilot 24-hour RPO and four-business-hour decision target, including asset manifest verification |
| R-07 | Temporary Sheets/database dual writes become permanent or diverge | Migration lead | One documented source of truth for each migration stage; no production dual-write code path; cutover checklist | Reconciliation finds writes in both stores, counts diverge, or source-of-truth record is missing | Stop new writes; choose documented source; reconcile deliberately; remove temporary path before next stage | Every stage names one source for content and leads; no production route performs permanent dual writes |
| R-08 | Uploads are unowned, unsafe, cross-site accessible, or left after cancellation | Platform operations owner | Server-generated `sites/<site_id>/assets/<asset_id>` keys; MIME/size validation; ownership checks; asset/revision references; deletion job | Upload authorization tests, storage inventory, orphan scan, cancellation deletion checklist | Revoke read URL/asset first; delete derivative/original as permitted; repair references; investigate exposure | Upload, read, delete, and cancellation tests prove a site cannot access another site's asset or leave untracked objects |
| R-09 | Draft, invalid configuration, or unsupported visual variant is published | Content/publishing owner | Immutable revisions; validation on import/save/publish/render; code-owned design/feature allowlists; visual baseline comparison | Publish validation result, revision audit event, screenshot/accessibility regression, invalid-variant test | Repoint to last known-good published revision; invalidate site cache; correct draft; rerun publish checks | Invalid/draft revisions cannot render publicly; both selected visual variants have approved baselines and rollback restores the expected revision |
| R-10 | Secrets, lead message text, or customer PII enters logs, screenshots, exports, or support evidence | Platform operations owner | Server-only credentials; structured safe logs; export access controls; screenshot policy; code review | Log redaction tests, secret scan, export review, incident report | Revoke exposed credential; restrict access; remove retained artifact where possible; assess customer notification requirements | Tests and manual review show no credentials or lead content in logs, visual baselines, or routine operational reports |

## Review cadence

- The migration lead reviews this register before every new roadmap stage and
  before enabling a customer hostname.
- The platform administrator records a named owner, current status, and any
  approved exception for each row at pilot launch.
- Any newly discovered isolation, lead, domain, or recovery issue adds a row
  before the affected site is re-enabled.

## Sources

- [PostgreSQL Row Security Policies](https://www.postgresql.org/docs/current/ddl-rowsecurity.html)
  for database policy behaviour and the need to account for privileged-role
  bypasses.
- [OWASP Authorization Cheat Sheet](https://cheatsheetseries.owasp.org/cheatsheets/Authorization_Cheat_Sheet.html)
  for least privilege, deny by default, per-request authorization, and tests.
- [Vercel custom-domain setup](https://vercel.com/docs/domains/set-up-custom-domain)
  for domain association, DNS verification, certificate, and test steps.
- [Next.js revalidateTag](https://nextjs.org/docs/app/api-reference/functions/revalidateTag)
  for targeted invalidation behaviour that requires cache-isolation tests.
- [Supabase Database Backups](https://supabase.com/docs/guides/platform/backups)
  for backup/PITR limits and restore planning.
