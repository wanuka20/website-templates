# v0.5.6 Gym Pilot Cost and Growth Assumptions

## Purpose

This is a planning estimate, not a purchase order or a promise of a fixed
bill. Prices and included usage can change, so the platform administrator must
recheck the linked provider pricing when selecting a plan or enabling a paid
feature. The estimate deliberately uses one repository, one Vercel project,
and one future managed PostgreSQL database; it does not multiply infrastructure
by customer site.

## Pilot assumptions

| Assumption | Planning value | Why it is reasonable for the first pilot |
| --- | --- | --- |
| Active customer sites | 2 Gym sites | The roadmap requires a two-customer isolation pilot. |
| Public traffic | 3,000 sessions per site per month; 6,000 total | Enough to exercise caching and real customer usage without assuming marketplace-scale traffic. |
| Lead volume | 50 validated leads per site per month; 100 total | Leads are small relational records; cost is dominated by the database base plan, not this row count. |
| Content revisions | 10 published/draft revisions per site per month | Supports normal editor corrections and rollback practice. |
| Source media | 25 images per site, average 2 MB; about 100 MB total before derivatives | Leaves room for hero, trainer, gallery, and logo assets. |
| Database data | Less than 0.5 GB for structured content, revisions, leads, and audit metadata | The initial Gym data model is text/list heavy and deliberately stores large media outside PostgreSQL. |
| Monthly image/CDN transfer | 25 GB planning allowance | Provides headroom over the expected small pilot while making image/egress usage visible. |
| Backup/recovery | Daily provider backup plus weekly encrypted logical export | Meets the pilot's 24-hour RPO planning baseline without buying PITR immediately. |

These are sizing assumptions only. The first two real customers may differ;
measure actual storage, database size, egress, lead count, and support time
monthly instead of treating the table as fact.

## Current reference pricing and pilot envelope

The sources were checked on 2026-07-28. They are used as a transparent
reference for a budget decision, not as an approval to subscribe or spend.

| Cost area | Current planning assumption | Estimated monthly cost (USD) | Notes |
| --- | --- | ---: | --- |
| Managed PostgreSQL | Supabase Pro with the included paid-plan compute credit/micro project | 25 | Supabase currently lists Pro from USD 25/month, including 8 GB database disk, 100 GB file storage, 250 GB egress, and daily backups retained for 7 days. |
| Existing hosted application | One existing Vercel project | 0 incremental if the existing team plan already covers the pilot | Do not create a project per Gym. |
| Vercel commercial plan, if not already paid | One Vercel Pro seat/project team | 20 | Vercel currently lists Pro at USD 20/month with included usage credit. Treat this as platform cost, not a per-site cost. |
| Weekly encrypted export / asset manifest | Existing controlled backup storage allowance | 0-5 | Provider/storage choice is still open; reserve a small allowance until a concrete storage provider is selected. |
| Monitoring/alerts | Existing logs plus minimal alerting | 0-10 | Use included capability first; price a dedicated product only when the observability work defines a need. |
| Customer domains | Customer-owned and paid directly by the customer | 0 platform estimate | Excluded because the product boundary lets customers use their own domains; record any exception separately. |
| Optional PITR | Not selected for pilot | 0 | Supabase currently lists roughly USD 100/month for seven-day PITR. Enable only if the 24-hour RPO is unacceptable. |

**Pilot budget conclusion:**

- If Vercel Pro is already paid for the existing project, plan **USD 25-40 per
  month incremental** for the database, backup allowance, and basic monitoring.
- If Vercel Pro is newly required for commercial hosting, plan **USD 45-60 per
  month total platform cost** before overages.
- Set a **USD 75/month pilot alert threshold**. An expected overage needs a
  written decision before disabling provider spend caps or enabling add-ons.

This estimate excludes labour, taxes, payment processing (out of scope), and
customer-owned domain renewal. It also excludes a costly RPO improvement such
as PITR; that is intentional, visible risk rather than a surprise bill.

## Growth model and revisit triggers

Review the provider dashboard and this estimate monthly during the pilot, and
immediately when any trigger below occurs:

| Trigger | Required decision |
| --- | --- |
| More than 5 active sites or more than 15,000 monthly sessions | Recheck Vercel usage, cache hit rate, domain operations time, and support capacity. |
| Database data exceeds 4 GB, or file storage exceeds 50 GB | Reprice database/storage tiers and archive/reduce unused assets before scaling by habit. |
| Egress exceeds 125 GB/month, or an image-heavy campaign is planned | Verify image sizes, CDN/cache behaviour, and provider overage pricing. |
| More than 1,000 leads/month, or more than 10 customer support lead investigations/month | Re-evaluate indexes, durable rate limiting, lead retention tooling, and internal manager scope. |
| Actual monthly platform cost reaches USD 75 | Review usage, spend caps, customer pricing, and whether an upgrade is justified. |
| A customer requires an RPO shorter than 24 hours or RTO shorter than four business hours | Price PITR, higher-tier support, and more frequent restore rehearsals before accepting the requirement. |
| Two successful pilot sites complete 90 days | Replace estimates with measured data and decide whether the next template family may migrate. |

## Cost-control rules

1. Keep one shared database and project. A separate database/project is an
   exception requiring a security, contract, or scale decision with a written
   cost owner.
2. Set provider spend caps/alerts before enabling paid overages. Never assume
   a free tier is suitable for an active commercial pilot.
3. Optimise image size and cache behaviour before buying egress capacity.
4. Store media in object storage, not in database rows; track originals and
   derivatives per `site_id` so cancellation removes unused cost.
5. Rehearse restore with the included daily-backup policy before purchasing
   PITR. Escalate only when measured RPO/RTO or a customer requirement proves
   it necessary.
