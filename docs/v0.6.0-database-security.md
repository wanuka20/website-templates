# v0.6.0 Gym Database Security

## Scope and status

This document defines the first PostgreSQL authorization boundary for the
Gym-only shared platform. The implementation is foundation migration
`db/foundation/migrations/0002_gym_database_security.sql`.

The migration was applied to the separately approved synthetic-only Neon
staging project on 2026-08-02. Live checks proved that each seeded Gym hostname
context could see only its own site and published revision. No Vercel variable,
production route, Google Sheet, Apps Script endpoint, customer domain, live
lead, or production database was changed. Production still requires a
separate approval and security review.

## Roles and credentials

The migration creates two NOLOGIN capability roles:

| Role | Purpose | Allowed access |
| --- | --- | --- |
| `website_templates_runtime` | Future public server runtime | Resolve an active Gym hostname through the private function, read that active site and its selected published revision, and insert a validated lead for that site |
| `website_templates_migrator` | Reviewed schema/data migrations | Explicit full RLS policies and schema-management privileges; never used by public application requests |

Both roles are `NOSUPERUSER`, `NOCREATEDB`, `NOCREATEROLE`, `NOREPLICATION`,
and `NOBYPASSRLS`. They deliberately have no password and cannot log in.
Local, staging, and production each need separate LOGIN credentials that are
created outside Git and granted exactly one capability role. Never reuse the
migration credential in the application or give the runtime login membership
in the migrator role.

The future connection variables remain server-only. They must not use a
`NEXT_PUBLIC_` prefix, enter browser bundles, appear in reports, or be copied
between local, staging, and production.

## Deny-by-default access

The migration removes public table, sequence, function, and schema-creation
access. It enables and forces row-level security (RLS) on `customers`, `sites`,
`domains`, `site_content`, `site_revisions`, and `leads`.

With forced RLS, even a table owner is subject to policies unless it is a
superuser or has `BYPASSRLS`. Neither capability role can bypass RLS. Tables
without a matching policy are therefore denied even if a SQL grant exists.

The runtime role intentionally receives no access to:

- customer records;
- the domains table directly;
- mutable/draft `site_content`;
- draft, superseded, or unselected revisions;
- reading leads;
- changing lead status or delivery status; or
- updating or deleting any foundation record.

The future internal manager needs authenticated actor/site membership and its
own policies in v0.6.4. Do not widen the public runtime role to build it.

## Trusted site context

RLS cannot use a browser-supplied `site_id`. It also does not rely on a custom
PostgreSQL session setting because ordinary roles can set custom parameters.

`app_private.activate_site_context(hostname)` accepts a normalized hostname and
resolves exactly one active domain attached to an active Gym site. It signs the
resolved site ID together with the PostgreSQL backend process and transaction
ID using a random key stored in the private schema. The signed values are
transaction-local, preventing pooled connections from reusing another
request's tenant context. A runtime role can change a custom setting but cannot
forge the matching signature for another site.

The future server repository must use one transaction per request:

1. Begin a transaction.
2. Call `app_private.activate_site_context()` with the trusted request
   hostname.
3. Stop with a safe not-found response if it returns `NULL`.
4. Execute only the site-scoped repository queries.
5. Commit or roll back, releasing the transaction-bound context.

The runtime cannot set a raw site ID through the private API. Unknown, pending,
failed, removed, suspended, malformed, or non-Gym hosts do not activate a
context.

## Runtime policies

- `sites`: select only the active Gym site matching the transaction context.
- `site_revisions`: select only the context site's published revision that is
  currently referenced by `sites.published_revision_id`.
- `leads`: insert only when the row's `site_id` matches the transaction
  context. The runtime can supply only contact/source columns; IDs, statuses,
  delivery state, and timestamps stay database controlled.

The hostname resolver is a narrow `SECURITY DEFINER` function owned by the
NOLOGIN migrator role. Public function execution is revoked. Its fixed
`search_path` and schema-qualified tables prevent search-path substitution.
The policy helper is wrapped in a scalar subquery so PostgreSQL can evaluate
the signature once per statement rather than once per candidate row.

## Validated writes

Database authorization is not content validation. Future content writes must
first parse the complete record with `lib/gym-content-model.ts`. The database
then reinforces schema version 1, the exact six boolean feature flags, fixed
visual variants, required JSON object shapes, and relational constraints.

Lead writes must pass the server-side Zod validation already used by the lead
route. Matching database checks enforce the accepted name, email, phone,
subject, message, and source-route length limits. These checks do not replace
the honeypot, hostname resolution, or future durable rate limiting.

## Verification status and production gate

Static tests cover the migration contract. The approved staging execution also
proved the two positive tenant-read cases with the runtime capability role.
The SQL editor's admin role was granted temporary runtime membership only for
those transaction-bound checks, then that membership was immediately revoked.

Before any production apply, repeat the complete list below against a fresh
disposable local database or dedicated staging LOGIN roles:

1. Runtime can resolve and read site A's published revision.
2. Runtime cannot read site B after site A context is active.
3. A new transaction has no stale context.
4. Runtime cannot read customers, domains, drafts, mutable content, or leads.
5. Runtime cannot update/delete rows or set lead status/delivery fields.
6. Runtime can insert a valid lead only for the resolved site.
7. Runtime cannot activate pending, removed, suspended, unknown, malformed, or
   non-Gym hosts.
8. Invalid schema versions, flags, content records, and lead lengths fail.
9. The real runtime LOGIN role is `NOSUPERUSER` and `NOBYPASSRLS` and has no
   migrator membership.

The two-site read checks are live RLS evidence, but they are not the complete
negative-policy test matrix above. Apply to production only after a separate
approval, backup check, dedicated LOGIN-role matrix, and staging evidence
review.
