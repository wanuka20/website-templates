## Timestamp policy

- Every database timestamp in the foundation schema is `timestamptz`.
- Migration `0003_gym_timestamps_and_recovery.sql` sets the database,
  migrator capability role, and runtime capability role timezone defaults to
  `UTC`. Environment-specific LOGIN roles must also be created with `UTC` as
  their default.
- Application and machine-readable timestamps use ISO 8601 UTC, such as
  `2026-08-01T19:00:00.000Z`.
- Human-facing operational timestamps use the IANA timezone
  `Asia/Colombo`, rendered with an explicit offset, such as
  `2026-08-02 00:30:00 +05:30`.
- `lib/operational-time.ts` is the code-owned conversion boundary. Callers
  must pass an instant with a timezone or offset; they must not treat a bare
  local date/time as canonical data.

PostgreSQL stores `timestamptz` instants internally as UTC and converts their
display using the current session timezone. Keeping database sessions in UTC
prevents console output, exports, and machine comparisons from silently using
a workstation or provider timezone.

## Backup configuration baseline

### Synthetic staging

The approved dedicated Neon Free project uses a six-hour history window and
one manual snapshot. Its baseline is:

1. Use a project separate from rehearsal and production, containing synthetic
   or sanitised data only.
2. Keep the foundation source branch protected from test resets.
3. Capture a named manual snapshot immediately before the restore rehearsal.
4. Restore into a separate validation branch. Never overwrite the source
   branch for the first recovery action.
5. Retain the source manifest and restore report under
   `reports/gym-foundation-recovery/` without credentials or row contents.

The retained manual snapshot is labelled
`production at 2026-08-02 11:45:29 UTC (manual)`. It restored in 1.42 seconds
into branch `v0.6.0-restore-proof-2026-08-02`; this observed synthetic result
is not a production recovery-time guarantee. Free-plan history is suitable for
this staging proof, but it does not by itself meet the pilot's 24-hour
recovery-point objective.

### Future production

Production remains unprovisioned and unapproved. Before a real Gym goes live:

- use the separately approved Neon Launch production project;
- configure the longest approved history window, up to the current Launch
  limit of seven days;
- take a manual snapshot before every production migration or cutover;
- retain one encrypted weekly logical `pg_dump` export for 35 days in a
  private backup location, after the storage owner, encryption method, access
  list, retention deletion, and restore procedure are selected;
- record backup health weekly and rehearse recovery at least once before pilot
  launch and after a database-provider or backup-policy change.

The production objectives remain a maximum 24-hour recovery point and a
four-business-hour decision on a validated recovery. They are targets, not
claims of current capability. Neon history, snapshots, and logical exports
cover PostgreSQL data only; future uploaded images require a separate asset
backup and restore policy.

## Read-only restore proof

The verifier compares all six foundation tables using row counts and SHA-256
hashes of deterministic row representations. It never writes to either
database and never includes customer content, lead fields, or connection
strings in its evidence files.

1. Put a maintenance/read-only staging source connection in ignored
   `.env.local` as `GYM_FOUNDATION_RECOVERY_DATABASE_URL`, set
   `GYM_FOUNDATION_RECOVERY_TARGET=staging-source`, and run:

   ```powershell
   npm.cmd run db:foundation:recovery:capture
   ```

2. Record the UTC capture time, create the provider snapshot, and restore it
   into a separate validation branch.
3. Change only the ignored connection variable to that validation branch, set
   `GYM_FOUNDATION_RECOVERY_TARGET=staging-restore`, and run:

   ```powershell
   npm.cmd run db:foundation:recovery:verify
   ```

4. The proof passes only when source and restore counts and hashes match for
   `customers`, `sites`, `domains`, `site_content`, `site_revisions`, and
   `leads`; both sessions report `UTC`; and no foundation column uses
   `timestamp without time zone`.
5. Confirm the source branch remains unchanged, record actual elapsed restore
   time, and retain safe provider snapshot/branch identifiers in the evidence.
   Do not record credentials.

The scripts deliberately require a target label. That label is a guardrail,
not proof of environment identity; the operator must still verify the Neon
project and branch before connecting.
