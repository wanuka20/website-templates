# v0.6.0 Gym Template and Content Model

## Decision

The database-backed Gym path uses one code-owned template key, one versioned
content schema, named visual variants, and named feature flags:

- `template_key` is always `gym` for the first sites.
- `schema_version` is `1` for the initial content document.
- `content` contains validated Gym marketing content only.
- `visual_variant` is either `classic` or `editorial`.
- `feature_flags` contains only the named boolean flags defined below.

The runtime contract is implemented in `lib/gym-content-model.ts`. It is the
application-level validation boundary for future database reads, writes,
imports, draft saves, publishing, and rendering. PostgreSQL constraints still
enforce the fixed template key, supported visual variants, object-shaped JSON,
and tenant relationships; the full nested JSON validation belongs to the
server application schema.

This task defines the contract only. It does not connect PostgreSQL to a public
route, change Google Sheets, create a database, configure Vercel, or submit a
lead.

## Stored record

```text
GymContentRecord
  template_key       "gym"
  schema_version     1
  content            validated GymContent
  visual_variant     "classic" | "editorial"
  feature_flags      GymFeatureFlags
```

`content` intentionally excludes the legacy `themeTemplate` field. A database
record stores its visual choice in `visual_variant`, so content cannot choose a
renderer through an unvalidated Sheet value. The current Google Sheets demo
path keeps its existing `themeTemplate` fallback until its later migration.

## Gym content

Version 1 preserves the current public `GymConfig` marketing scope:

- brand, contact, hero, about, social, WhatsApp, and SEO values;
- membership marketing plans and safe enquiry/external links;
- trainers and certifications;
- class schedule entries;
- testimonials;
- gallery images; and
- amenities.

The schema requires the complete document, rejects unknown properties, accepts
only HTTPS or root-relative image references, rejects unsafe action links,
constrains numbers and text lengths, and requires unique IDs within each nested
collection. It does not accept arbitrary HTML, CSS, JavaScript, database
queries, customer-name switches, or unsupported template fields.

## Visual variants

The named variants are `classic` and `editorial`. The allowlist is exported by
`lib/gym-content-model.ts` and reused by `config/gym-design.ts`, preventing the
database contract and renderer selector from drifting into separate lists.

The legacy Sheet route may continue to use the current Classic fallback for a
missing or invalid `themeTemplate`. A future database-backed write or publish
must instead reject an unsupported `visual_variant`; it must not guess a
renderer or check a customer name.

## Feature flags

The initial flags are:

| Flag | Controls |
| --- | --- |
| `membership` | Membership-plan section and actions |
| `trainers` | Trainer profiles |
| `classSchedule` | Class schedule |
| `testimonials` | Customer testimonials |
| `gallery` | Gallery section |
| `whatsapp` | Floating and section WhatsApp actions |

All six default to `true`, preserving the current public Gym behavior. Unknown
flag names and non-boolean values are rejected. Brand, hero, about, contact,
and SEO are part of the required website contract and are not optional feature
flags in version 1.

This model only defines the flags. The database-backed renderer will apply
them after site-aware data access is introduced; this task does not change the
current Sheet-backed public rendering path.

## Versioning and future changes

`schema_version` changes only when the persisted Gym content shape changes.
A future version needs an explicit normalization/migration function, tests for
old and new documents, and a publishing decision. Existing published content
must not be mutated invisibly.

New visual variants and feature flags are code changes: add them to the central
allowlist/schema, implement shared behavior, and test them before stored data
may select them. Customer-specific differences remain data; customer-specific
copies or name checks do not belong in the shared Gym components.

## Verification boundary

Unit tests prove the current built-in Gym content passes and that the contract
rejects a different template key, unknown visual variants, unknown feature
flags, unknown content fields, unsafe links, and duplicate nested IDs. The RLS
and role migration is now defined in `0002_gym_database_security.sql`; actual
PostgreSQL role/policy execution, site-aware access, publishing, and two-site
seed tests still require their documented local/staging gates.
