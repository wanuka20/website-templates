# v0.5.6 Gym-First Platform Plan

## Purpose

This document records the decisions that define the first Gym-focused stage of
turning `website-templates` into a hosted, multi-customer platform. It is a
planning boundary, not an implementation of accounts, payments, or a new Gym
management system.

## 1. Product boundary

The Gym product is currently a public business website that helps a Gym present
its brand and receive enquiries.

### In scope

- Brand content and business information.
- Membership enquiries and membership-plan marketing.
- Trainer profiles.
- Class schedules.
- Gallery and testimonials.
- SEO content and metadata.
- WhatsApp contact actions.
- Validated contact leads.

### Explicitly out of scope

The platform will not build or operate the following during the Gym-first
rollout:

- Member accounts, sign-in, passwords, or other member authentication.
- Payments, subscriptions, invoices, refunds, or payment records.
- Attendance, check-ins, or access control.
- Trainer payroll, commissions, or staff compensation.
- A complete booking system or customer-relationship-management (CRM) product.

### How a request can change this boundary

A requested feature may move into scope only when it is validated with all of
the following information and then approved as a deliberate roadmap change:

1. The specific customer and user problem it solves.
2. The real Gym workflow it must support.
3. The data that would be stored, accessed, or changed.
4. Required integrations, operating cost, and ongoing support work.
5. Security, privacy, and compliance implications.
6. A small pilot and clear acceptance test that proves the feature is needed.

This avoids accidentally turning a website and enquiry product into a Gym
operations platform because one customer asks for a convenient extra feature.

## 2. Membership-card rule

Membership cards are marketing and enquiry actions only. Their normal
destinations are the Gym contact form, WhatsApp, or another customer-controlled
enquiry page.

An external checkout link may be shown only when it belongs to a third-party,
customer-owned checkout service. The platform must not collect payment details,
store payment or subscription state, create invoices or refunds, or integrate
with that checkout provider. In other words, the link can take a visitor away,
but `website-templates` does not become the payment system.

## 3. Shared-platform decision

The future Gym platform will use:

- One `website-templates` repository.
- One primary Vercel project.
- One shared managed PostgreSQL database.
- One unique `site_id` for every customer site.

The `site_id` is the trusted boundary between customers. It controls the
site's domain or temporary platform subdomain, content, visual style, lead
destination, cache namespace, and uploads. Shared Gym components remain shared
code; customer differences must be stored as site data, not copied into
customer-specific components.

Site identity must be resolved on the server from the incoming hostname. Browser
input such as a business name, template name, or claimed site ID cannot decide
which customer's data is read or where a lead is stored. Unknown, duplicate,
disabled, or unverified domains must fail safely. These rules prevent one
customer's content, leads, cached pages, or uploads from leaking into another
customer's site.

## 4. Remaining v0.5.6 defining tasks

Complete these tasks in order before the database migration work begins.

1. **Define per-site data and customization.** Specify which Gym values become
   site data: content, feature flags, domains, lead destination, uploads,
   status, and a validated per-site visual selection. Replace the current
   global visual fallback only during the database migration; keep the existing
   Gym renderers shared.
2. **Define lifecycle and retention.** Document customer and Gym-site creation,
   draft/published/suspended/cancelled states, content export, retention and
   deletion timing, and domain removal. State who can perform each action.
3. **Estimate cost and growth.** Record expected pilot Gym sites, monthly leads,
   images and storage, bandwidth, backups, and projected monthly cost before
   choosing a paid database plan.
4. **Create the migration risk register.** For every risk, record its owner,
   prevention, detection signal, response, and rollback path. At minimum cover
   data loss, cross-site access, cache leakage, failed lead delivery, broken
   domains, provider outage, rollback failure, and accidental permanent dual
   writes to Google Sheets and the database.
5. **Capture visual baselines.** Save representative desktop and mobile
   screenshots for the current Gym designs before the data layer changes. Use
   them with interaction and accessibility checks to prove the migration did
   not accidentally change the public website.

## Completion check

v0.5.6 is ready to hand over to the migration-rehearsal stage only when these
decisions are documented, the boundary has been approved, the risk register has
an actionable owner and rollback path for each material risk, and the Gym
desktop/mobile baselines have been captured without sending live test leads.

## 5. Per-site data and customization plan

### The recommendation in one sentence

Run one shared application, but treat every Gym website as one `site` with an
opaque `site_id`; resolve that ID only on the server from the request hostname,
then use it as a required boundary for every tenant-owned database row, cache
entry, upload, lead, permission check, and published content read.

This is a *shared-database, shared-schema* model. It keeps the operating cost
and maintenance of one repository, Vercel project, and PostgreSQL database,
without treating a customer name, URL path, browser field, or template name as
proof of which customer's data may be used.

### 5.1 What belongs to a site

The first database-backed Gym model should make the `site` the operational
tenant. A customer can own one or more sites, but every public website and its
data has one `site_id`.

| Data group | Recommended owner | First release contents |
| --- | --- | --- |
| Customer relationship | `customers` | legal/display business name, support contact, lifecycle notes; not public page content |
| Website identity | `sites` | opaque ID, `customer_id`, `template_key = "gym"`, status, platform subdomain, selected published revision, timestamps |
| Domain aliases | `domains` | normalized hostname, `site_id`, primary/canonical flag, requested/pending/verified/active/failed/removed status, verification metadata |
| Public Gym content | `site_content_revisions` | validated `GymConfig`-shaped content, visual variant, feature flags, schema version, draft/published state, author and timestamps |
| Public media | `site_assets` | `site_id`, storage key, MIME type, byte size, safe dimensions, alt text, ownership and lifecycle state |
| Enquiries | `leads` | `site_id`, contact fields, source route, safe delivery status, timestamps, retention/deletion state |
| Site access | `site_memberships` | `site_id`, user/actor ID, role, status, invitation/audit timestamps; add only with the internal manager |
| Audit and operational events | `site_events` or the log provider | `site_id`, event type, request ID, safe status/error metadata; never message content or credentials |

Use a normal `customers` to `sites` relationship even for the first pilot. It
prevents a painful redesign if one Gym later has a second location, a temporary
campaign site, or a staging preview. A `customer_id` is useful for commercial
ownership; `site_id` is the stricter runtime isolation boundary.

Every tenant-owned table must have a non-null `site_id` and foreign key to
`sites(id)`, even when it also has `customer_id`. Foreign keys and database
constraints should reject orphan rows. Unique identifiers that are meaningful
only inside a site must be scoped, for example `UNIQUE (site_id, external_key)`
or `UNIQUE (site_id, slug)`. Do not rely on a developer remembering an ad-hoc
`WHERE site_id = ...` clause.

### 5.2 Data that must remain platform-global

The following are platform-controlled, not customer-editable site data:

- The repository, deployed application version, Vercel project, database
  connection settings, secrets, backups, and observability configuration.
- The code-owned Gym content schema and its supported schema versions.
- The code-owned allowlist of `GymDesign` values (`editorial` and `classic`
  today), renderer map, shared components, accessibility rules, and security
  headers.
- The rules that validate URLs, uploads, SEO lengths, feature flags, domain
  states, and lifecycle transitions.
- The platform role catalogue and the authorization policy that determines who
  may create a customer, change a domain, publish content, read leads, or
  delete an asset.
- Platform-wide product settings such as supported templates and internal
  operational limits. Store a value globally only when changing it for one Gym
  would make no sense.

This distinction matters: a customer may choose from approved designs and
content options, but they must not upload executable code, arbitrary CSS or
JavaScript, database queries, server-side environment settings, or a new route.
That keeps one tested product rather than a collection of fragile forks.

### 5.3 Recommended first content model

Keep the current `GymConfig` as the public rendering contract during migration.
The database-backed equivalent should store a validated snapshot of this shape
with the following envelope:

```text
site_content_revisions
  id, site_id, template_key, schema_version
  content_json                 // validated GymConfig-compatible marketing content
  visual_variant               // one value from the code-owned GymDesign allowlist
  feature_flags_json           // only documented, code-owned boolean/enum flags
  state                        // draft | published | superseded | rolled_back
  created_by, created_at, published_at, supersedes_revision_id
```

`sites.published_revision_id` identifies the only content revision that a
public hostname may render. Drafts must never be returned to a public request,
and publishing should be one transaction that validates the revision, marks it
published, points the site to it, emits a safe audit event, and invalidates that
site's cache tags.

For the Gym pilot, use a versioned JSON document for the marketing content and
keep high-risk or operational data relational: domains, leads, uploads,
memberships, and revisions. This is intentional. The existing `GymConfig`
contains nested lists of trainers, plans, classes, testimonials, galleries, and
amenities. A validated revision document lets the migration preserve that
shape, roll back one complete public version, and avoid creating many tables
before real editor requirements are known. Add dedicated relational tables only
when a real workflow needs querying or independent lifecycle management, such
as reusable assets, lead triage, or scheduling operations.

The content document includes the current public values: brand and contact
details, hero/about text and images, membership marketing plans and their
links, trainers, classes, testimonials, gallery, amenities, SEO, social links,
and WhatsApp settings. Membership links remain marketing/enquiry links. An
external checkout URL is permitted only when it is a validated HTTPS link to a
customer-owned third-party checkout; the platform does not process payment
details, store payment state, or call the checkout provider.

### 5.4 Customization layers and guardrails

Apply customization in this order, from least to most customer-specific:

1. **Code-owned template contract.** Shared components, allowed designs, field
   names, validation, interactions, and accessibility behaviour are released
   with the application. No customer-name conditionals belong here.
2. **Site visual selection.** Each site selects one validated `GymDesign`.
   The current global fallback in `config/gym-design.ts` is only a demo/legacy
   fallback; the database-backed public path must use the site's stored value.
   If its value is missing or invalid, do not silently choose another design in
   production: use the last valid published revision or fail the publish step.
3. **Site design tokens, only when a supported renderer uses them.** Allow a
   small named set such as approved colour pairs, logo, and image crop/focal
   point. Validate hex colours, dimensions, and image references. Do not accept
   free-form CSS.
4. **Site marketing content.** Text, images, lists, links, metadata, and
   feature flags are editable only through the matching schema. Store plain
   text or safely sanitised rich text; never render customer HTML directly.
5. **Platform-only operations.** Domain verification, publishing, suspension,
   rollback, retention, cross-site exports, and deletion need explicit roles
   and audited server actions.

Server validation is the source of truth. Reuse the TypeScript types for
developer clarity, but introduce a runtime schema (for example, Zod) because
database rows, migrations, and future admin requests are untrusted at runtime.
The same schema must validate before import, draft save, publish, render, and
write. Database constraints complement—not replace—that schema.

Minimum validation rules:

- Require a valid `template_key`; a Gym site can use only `gym` in this phase.
- Require a `visual_variant` from the code-owned allowlist. Reject unknown
  values instead of guessing a renderer.
- Validate text presence and length, numeric ranges, list sizes, stable item
  IDs, SEO title/description lengths, and permitted class levels.
- Allow only HTTPS external URLs for social, WhatsApp, membership, and media
  destinations; apply a purpose-specific allowlist where one exists. Reject
  `javascript:`, `data:`, credentials in URLs, and untrusted redirect targets.
- Store uploads under a server-generated, site-prefixed key such as
  `sites/<site_id>/assets/<asset_id>`. Never take a storage key or `site_id`
  from the browser as authority.
- Preserve `schema_version` with every content revision. Write an explicit
  migration/normalization function for each schema change; do not mutate old
  published documents invisibly.

### 5.5 Trusted hostname-to-site resolution

Public requests must use one server-side resolver before content, metadata,
assets with private access, or lead handling. Its job is simple:

1. Read the request hostname from the platform's trusted request context, not
   a browser form field, URL query, `businessName`, claimed template, or
   client-supplied `site_id`.
2. Remove a port, lowercase it, remove a trailing dot, reject malformed hosts,
   and apply the same normalization when a domain is created.
3. Find exactly one `domains` record with that normalized hostname whose site
   is active and whose domain is active/verified. The database must enforce a
   globally unique normalized hostname.
4. Return only a small, server-owned resolution result: `site_id`,
   `template_key`, canonical hostname, and public status. Unknown, duplicate,
   disabled, pending, or unverified domains return a safe not-found response;
   they must not fall back to another Gym's content.
5. Load the site's one published revision through its `site_id` and
   `published_revision_id`, then select the already-validated renderer.

Use a deterministic platform subdomain while a customer-owned domain is
pending, but represent it as a normal domain record and pass it through the
same resolver. DNS reaching Vercel proves routing, not which site should get
the request; the application database remains the authority for site ownership
and status. Keep `/templates/gym` as the existing demo/visual-test route during
migration and never treat it as a customer hostname.

For preview deployments, default to no customer data. Permit only explicit
development/test domains mapped to seeded test sites. This avoids accidentally
making live tenant content available from an arbitrary preview hostname.

### 5.6 Permissions and database isolation

There is no customer login in the public Gym scope today. The first public
roles are therefore deliberately narrow:

| Actor | May do | Must not do |
| --- | --- | --- |
| Public visitor | Read the resolved site's published public content; submit a validated lead to that resolved site | Choose another site, read drafts/leads/assets, or change content |
| Platform administrator | Create customers/sites, verify domains, publish/suspend/rollback, manage support and retention | Use a browser-exposed database credential |
| Site manager (future internal manager) | Edit and publish only assigned sites, view only assigned-site leads | Create other customers, access another site's data, bypass domain verification |
| Content editor (future) | Save drafts for assigned sites | Publish, manage domains, or read leads unless separately granted |

Every server query and mutation must receive the resolved or authorized
`site_id` from a server-side data-access layer. Do not expose a generic query
that accepts a raw site ID from the browser. On a future authenticated admin
request, first establish the actor, then verify the actor's membership and role
for the requested site, then execute the scoped operation. Check authorization
on every request and on every mutation, not merely when the admin page loads.

Use least-privilege database credentials and keep privileged credentials only
on the server. If the chosen PostgreSQL provider supports row-level security
(RLS), enable it for every tenant-owned table and write separate `SELECT`,
`INSERT`, `UPDATE`, and `DELETE` policies with both read and write checks. RLS
is defence in depth, not a replacement for the server data-access layer:
PostgreSQL table owners, superusers, and roles with `BYPASSRLS` can bypass it.
Use a non-owner application role where practical, keep migration/maintenance
roles separate, and test the actual production connection role.

### 5.7 Cache, lead, and upload partitioning

The current Sheets loader uses the broad cache tag
`template-content:gym`. That is acceptable only while there is one Gym
configuration. The database-backed path must never use a template-only cache
identity for site content.

Use a site-specific, non-PII cache namespace such as:

```text
site:<site_id>:resolution
site:<site_id>:content
site:<site_id>:revision:<revision_id>
site:<site_id>:metadata
```

The cache key, tag, and any lookup function arguments must include `site_id`
and the published revision ID where applicable. On publish, domain change,
suspension, rollback, or asset replacement, invalidate only that site's
resolution/content/metadata tags and relevant paths. Next.js documents that
tag invalidation is on-demand and may serve stale content while it refreshes;
that is acceptable for ordinary content edits only after a test proves a cache
entry cannot be shared across hostnames. Security- or status-changing actions
must take effect conservatively: stop serving content first, then invalidate
all site tags and confirm the unknown/suspended-domain response.

The lead endpoint must resolve the hostname server-side using the same resolver
as rendering. It may retain the current client `template` value only as a
validated compatibility field during migration, never as routing authority. It
must write the derived `site_id`, server-derived canonical/source hostname,
and request ID with the lead. Reject a form post from an unknown, disabled, or
unverified hostname. Do not trust a client `businessName`, `site_id`, storage
path, destination URL, or tenant header.

Uploads must be authorised against the actor's assigned site before creating a
server-generated key. Read/download URLs must verify asset ownership or use
public immutable assets that are safely scoped by `site_id`. CDN/cache paths,
image transformation keys, and deletion jobs must include the asset/site
identity so replacing or deleting one Gym's image cannot affect another.

### 5.8 Configuration, revisions, and lifecycle

Treat published configuration as versioned product data, not a mutable bag of
settings:

- Each revision has a content schema version, visual variant, flags, author,
  timestamp, and parent revision.
- A draft is editable; a published revision is immutable. A correction creates
  a new draft/revision instead of overwriting history.
- Publishing validates the complete document, chooses one canonical revision,
  writes an audit event, and invalidates the right site cache namespace.
- Rollback changes the `published_revision_id` to a known-good earlier
  revision; it does not manually reconstruct fields.
- Site status is explicit: `draft`, `active`, `suspended`, `cancelled`, and
  `deleted` (or equivalent documented states). Domain status is separate:
  `requested`, `pending_verification`, `active`, `failed`, and `removed`.
- Deletion follows a documented retention period. First disable public serving
  and writes, export what is required, then permanently delete only after the
  retention deadline and an authorised, auditable action.

### 5.9 Migration sequence

Follow the existing roadmap; do not skip straight from Google Sheets to live
custom domains.

1. **Finish v0.5.6 definitions.** Approve the data ownership, validation,
   lifecycle, role, cache, lead, upload, and risk decisions in this section.
   Capture desktop/mobile visual baselines for both Gym designs.
2. **v0.5.7 rehearsal.** Inventory every Gym Sheet field against the current
   `GymConfig`, export immutable backups, write a dry-run/idempotent importer,
   and migrate only copied non-production data. Report every transformed,
   missing, or rejected value.
3. **v0.6.0 foundation.** Create the schema, foreign keys, unique domain
   constraint, content-revision model, least-privilege roles, RLS where
   selected, backups, and two seeded test sites. No public route change yet.
4. **v0.6.1 site-aware data access.** Build the server-only resolver and
   repository functions. Add site-specific cache keys/tags and tests showing
   site A cannot load site B data. Keep the Gym components and typed renderer
   map shared.
5. **v0.6.2 controlled content migration.** Import one Gym into the database,
   compare every content field, image reference, SEO value, and lead count to
   the source. At each stage, name one source of truth; never leave permanent
   dual writes to Sheets and PostgreSQL.
6. **v0.6.3 domains and leads.** Turn on hostname resolution, site-aware
   metadata, server-derived lead routing, and controlled domain onboarding.
   Test active, pending, duplicate, disabled, and unknown domains.
7. **v0.6.4 manager.** Add the smallest internal authenticated editor,
   role checks, drafts/publish/rollback, lead views, and scoped uploads.
8. **v0.6.5 pilot and retirement.** Run two genuinely distinct Gym sites
   through content, leads, domains, cache, publishing, rollback, backup
   restore, and operational-cost checks before removing Gym Sheets from the
   production request path.

### 5.10 Required decisions before implementation

The following decisions need an explicit owner and record before v0.6.0:

1. Which managed PostgreSQL provider, ORM/query layer, and migration tool will
   be used, and whether its application role can enforce RLS without bypassing
   it.
2. Whether the initial internal manager is platform-admin only or includes
   customer site-manager accounts in the pilot.
3. The exact content schema and the supported `GymDesign`/feature-flag
   allowlists for the pilot.
4. The allowed third-party membership checkout domains and the intended visitor
   disclosure that checkout happens outside this platform.
5. Storage provider, allowed upload types/sizes, image processing policy,
   signed/public URL policy, backup policy, and deletion retention period.
6. The platform subdomain format, canonical-domain redirect rule, preview test
   hostname strategy, and manual domain verification owner.
7. Lead retention period, customer export process, operational access policy,
   and rate-limiting provider/limits.
8. The recovery objectives: acceptable content/lead data loss window, restore
   time target, backup frequency, and proof-of-restore test cadence.

### 5.11 Risks and proof before the pilot

| Risk | Prevention | Required proof |
| --- | --- | --- |
| Cross-site content, lead, upload, or cache leak | Required `site_id`, foreign keys, scoped repositories, RLS where chosen, site cache tags, server hostname resolver | Two-site integration tests intentionally try guessed IDs, swapped hosts, cache warm/cold reads, and asset URLs |
| Customer-controlled input selects another tenant | Do not trust client site/template/business fields; derive site server-side | Post a valid form body with another Gym's identifiers and verify it is stored only for the request hostname's site |
| Draft or wrong visual variant reaches public users | Published-revision pointer and allowlisted variants | Verify drafts/invalid variants cannot render; rollback restores the exact baseline screenshot |
| Domain takeover or incorrect routing | Unique normalized hostname, active/verified state, manual verification workflow | Verify duplicate/pending/disabled/unknown hosts return safe not-found and cannot resolve another site |
| Data loss or irreversible bad import | Immutable Sheet backup, dry run, idempotent importer, revision history, tested restore | Compare field/image/lead counts and restore a staging backup |
| Permanent dual-write inconsistency | One source of truth per migration stage | Document owner/source for content and leads; test a deliberate failure without divergent writes |
| Privileged access bypasses tenant rules | Server-only secrets, separate roles, least privilege, audited admin actions | Test with the actual app role and confirm it cannot read or write an unassigned site |

### 5.12 Test plan and completion gate

Before a real Gym pilot, automate the following in addition to type checks,
linting, production builds, visual screenshots, accessibility, and normal lead
tests:

- Schema tests: non-null `site_id`, foreign keys, scoped uniqueness, one active
  domain per normalized hostname, valid content revision states, and rejected
  unsupported variants.
- Resolver tests: localhost/test host, platform subdomain, active custom
  domain, uppercase/trailing-dot/port normalization, and safe failures for
  unknown, duplicate, disabled, pending, and unverified hosts.
- Authorization tests: public requests see only published content; each future
  site manager/editor is denied another site's content, lead, upload, domain,
  and publish operations; direct database/RLS checks use the real application
  role.
- Cache tests: warm site A then request site B on the same route; repeat after
  publishing, rollback, domain change, suspension, and asset replacement. The
  response, metadata, image URL, and cache tag activity must stay site-scoped.
- Lead tests: submit to each site's hostname; assert server-derived `site_id`
  and hostname, failure for an unknown host, honeypot behaviour, validation,
  rate limit, no cross-site read, and no real lead delivery in automated tests.
- Upload tests: reject an actor/site mismatch, unsafe MIME/type/size/path, and
  cross-site asset read/delete; verify an allowed asset renders only for its
  owner site.
- Recovery tests: restore a non-production backup, render the restored
  published revision, verify leads/content counts, and prove rollback does not
  delete historical revisions.

The first pilot may launch only when two seeded and then two real Gym sites
pass these isolation checks, share the same renderer code, have separately
verified domains or subdomains, and can each be published, suspended, rolled
back, backed up, restored, and operated without exposing the other site's
content or lead data.

## 6. Research basis

- [PostgreSQL row security policies](https://www.postgresql.org/docs/current/ddl-rowsecurity.html): RLS is disabled by default, uses policy-controlled reads/writes when enabled, and defaults to deny when no policy permits access. It also documents bypass considerations for table owners and privileged roles.
- [OWASP Authorization Cheat Sheet](https://cheatsheetseries.owasp.org/cheatsheets/Authorization_Cheat_Sheet.html): least privilege, deny by default, per-request authorization, secure handling of guessed identifiers, logging, and authorization tests.
- [Vercel for Platforms](https://vercel.com/kb/guide/nextjs-multi-tenant-application): a single codebase/deployment can serve tenant subdomains and custom domains; Vercel supports a middleware-based routing pattern.
- [Vercel custom-domain setup](https://vercel.com/docs/domains/set-up-custom-domain): domain association, DNS verification, certificate provisioning, and post-setup testing are separate steps that must be tracked.
- [Next.js `revalidateTag`](https://nextjs.org/docs/app/api-reference/functions/revalidateTag): tags support targeted cache invalidation; the recommended stale-while-revalidate behaviour means content updates need explicit site-scoped cache tests.
