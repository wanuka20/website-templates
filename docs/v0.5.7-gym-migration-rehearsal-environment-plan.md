# v0.5.7 Gym Migration Rehearsal Environment Plan

## Purpose

Before moving even one Gym from Google Sheets to the future shared PostgreSQL
platform, perform the whole migration process in a safe rehearsal environment.
The rehearsal is a dress rehearsal: it proves the import, validation,
reconciliation, tenant isolation, rollback, and evidence collection steps
without changing a customer site.

This is a **plan only**. It does not authorize creating a cloud project,
database, Vercel environment, deployment, migration tool, or connection. A
separate explicit user approval is required before any implementation or
external-service action begins.

## 1. Firm safety boundaries

The rehearsal environment must meet all of these rules:

- It is Gym-only. Restaurant, Salon, Real Estate, and Tuition are out of scope.
- It uses the agreed future shape: one shared-schema database, two synthetic
  Gym sites, and a non-null `site_id` on every tenant-owned row.
- It must never write to the production Google Sheet, Apps Script, customer
  domain, production database, or production Vercel deployment.
- It must never submit, forward, or store a real contact lead. All test leads
  are clearly synthetic and remain inside the local/non-production system.
- It must not copy production secrets, customer email/phone/address details,
  lead messages, customer images, or database rows into the rehearsal.
- It must not reuse the production connection string, service-role credential,
  Apps Script URL, customer domain, analytics key, payment credential, or
  email/WhatsApp delivery credential.
- It must not change the current public Gym route, its Google Sheets fallback,
  or the production lead route while the rehearsal is being planned.

The existing application currently reads Gym content from Apps Script and uses
the shared cache tag `template-content:gym`; it also sends public Gym leads to
Apps Script. That is legacy behaviour, not an approved rehearsal target. The
future rehearsal must make its own local data path explicit and prove that no
test request can reach either live integration.

## 2. Recommended safe shape

Start locally, with no cloud account or Vercel change:

```text
synthetic source fixture
        |
        v
dry-run importer ---> report only (no database writes)
        |
        v
local PostgreSQL-compatible database ---> site-scoped rendering and fake lead store
        |
        v
two local test hostnames / test clients
```

The local database is the first choice because it keeps the trial reversible,
cheap, and disconnected from customer systems. If the local proof later needs
a shared staging environment, it must be a separately created, non-production
database/project with different credentials and an explicit authorization.
It must not be a clone that contains real customer or lead data.

The selected provider is still to be approved. If Supabase is selected, its
official workflow supports local development, committed migration files, seed
data, and explicit `--local`/`--linked` commands. The plan requires the future
implementation to pass the target explicitly so a command cannot silently act
on a linked remote project.

## 3. Required components (future implementation)

| Component | Rehearsal purpose | Safe requirement |
| --- | --- | --- |
| Local database runtime | Holds only synthetic tables, revisions, domains, and fake leads | New local data volume; no production connection string or backup restore |
| Versioned schema migrations | Creates `customers`, `sites`, `domains`, content revisions, assets metadata, and leads | Migrations are reviewed and run locally first; all tenant-owned data has `site_id` |
| Synthetic source fixture | Represents a Gym Sheet export without contacting Sheets | Checked-in/generated test fixture with fictional brands, contacts, URLs, and image paths |
| Importer with dry-run mode | Transforms and validates fixture data | Dry run performs zero inserts/updates/deletes and emits a deterministic report |
| Database-backed reader | Loads only the published revision for a resolved test site | It obtains `site_id` only from a trusted local hostname resolver |
| Fake lead sink | Tests validation and `site_id` routing | Stores test-only records locally or records a no-delivery result; never invokes Apps Script |
| Evidence directory | Stores reports, checksums, row counts, and non-sensitive screenshots | No credentials, lead message text, customer data, or database dumps in Git |

## 4. Synthetic and sanitised data

Use **synthetic data by default**, not a production copy. Create two obviously
fictional Gyms, such as `Northstar Strength` and `Harbourline Fitness`, with
different names, colours, visual variants, test hostnames, plan labels,
trainers, image paths, and test lead counts. Their purpose is to make leakage
easy to spot: if either name appears on the other site, the test fails.

When mapping is impossible to understand without a source-shaped sample,
create a **sanitised schema fixture** instead of exporting data:

1. Retain only field names, field types, list lengths, and harmless category
   values needed to exercise the transformer.
2. Replace every person, Gym, phone number, email, address, URL token, lead
   message, image, and identifier with fictional values.
3. Regenerate IDs rather than hashing customer IDs; a hash can still be a
   persistent identifier.
4. Record fixture provenance as `synthetic` or `sanitised-schema-only`, never
   as a customer export.
5. Have the migration lead manually review the fixture before it enters Git or
   any shared test environment.

Do not download, scrape, or copy the live Sheet while building the rehearsal.
If a future migration needs an immutable production-source backup, that belongs
to v0.6.2 under a separate explicit approval and controlled access process.

## 5. Environment separation and secrets

Use an allowlisted environment profile rather than relying on names alone.

| Concern | Local rehearsal | Future staging (only if approved) | Production |
| --- | --- | --- | --- |
| Database | Local, new synthetic volume | Separate non-production project/database | Shared customer database |
| Data | Synthetic/sanitised only | Synthetic/sanitised only | Customer data |
| Hostnames | `northstar.test`, `harbourline.test` or equivalent local hosts | Dedicated staging-only names | Verified customer domains/platform subdomains |
| Lead delivery | Local fake sink or deliberate disabled state | Disabled or staging-only capture | Existing/future approved production delivery |
| Secrets | Local file ignored by Git, or process-only values | Staging-only secrets scoped to that environment | Production-only secrets |
| Apps Script/Vercel | No call, no write, no deployment | No production values | Live integration only while legacy path remains |

Future implementation must use distinct variable names or an explicit
environment mode, for example `GYM_DATA_SOURCE=rehearsal`, and fail closed if
it is combined with a production hostname, production database URL, or a
Google Apps Script destination. Credentials remain server-only and are never
added to source control, reports, screenshots, fixtures, or browser bundles.

Vercel documents separate Development, Preview, and Production variable
scopes. This plan does **not** authorize configuring them. If staging is later
approved, it needs staging-only values and a review that no production variable
is inherited accidentally.

## 6. Rehearsal sequence

Perform the future run in this order. Stop at the first failed gate; do not
"patch forward" by editing source data or overwriting a prior result.

1. **Preflight.** Confirm the working directory, environment mode, local
   database target, synthetic-fixture marker, and blocked Apps Script/lead
   endpoints. Record command versions and a run ID.
2. **Create schema locally.** Apply migrations to a newly created local
   database. Verify required foreign keys, non-null `site_id`, scoped unique
   constraints, and least-privilege application role before importing.
3. **Dry run.** Parse and validate the fixture without writes. Produce a
   report of fields read, transformations, warnings, rejected values, expected
   site/revision/asset/lead counts, and a fixture checksum.
4. **Review dry-run report.** Migration lead approves only zero unexplained
   required-field errors and zero forbidden external destinations. A warning
   is not an approval to continue.
5. **Disposable import.** Create a fresh local database, import once, and
   record inserted/updated/skipped/rejected counts. Run the same import again
   to prove idempotency: the second run must not duplicate rows or revisions.
6. **Reconcile.** Compare source-fixture and database records by explicit
   mapping: required fields, nested list counts, image references, SEO values,
   visual variant, revision state, and synthetic lead count. Explain every
   intentional transformation.
7. **Exercise tenant isolation.** Resolve each local hostname server-side;
   render each published site; attempt swapped hostnames, guessed `site_id`,
   swapped asset paths, and cross-site lead reads/writes. Each must return only
   the resolved site's permitted data or a safe failure.
8. **Exercise cache isolation.** Warm one site, then request the other site
   with the same routes. Verify content, metadata, cache keys/tags, and asset
   references stay tied to `site_id` and published revision, never the old
   template-only key.
9. **Exercise failure and rollback.** Inject one invalid record and one
   interrupted import in the disposable database. Confirm no partial published
   revision becomes public. Restore/recreate from the last clean local schema
   plus fixture, then rerun reconciliation.
10. **Record evidence and decide.** Save only safe reports and pass/fail
    results. The migration lead decides whether the plan is ready for v0.6.0/
    v0.6.2 implementation; no production cutover follows from a rehearsal.

## 7. Acceptance criteria and test evidence

The rehearsal passes only when all items below have evidence attached to its
run record.

| Gate | Required evidence |
| --- | --- |
| No live writes | Process/environment log shows local target; network test/guard proves Apps Script, customer hosts, and production database were not contacted |
| Data safety | Fixture review says `synthetic` or `sanitised-schema-only`; no real PII, image, secret, or lead message appears in repository evidence |
| Import quality | Dry-run report, fixture checksum, mapping report, and zero unexplained required-field differences |
| Idempotency | Two consecutive imports produce no duplicate tenant rows, revisions, assets, or leads |
| Reconciliation | Expected versus actual counts and per-field mapping for content, images, SEO, variant, and fake leads are explained and approved |
| Tenant isolation | Site A/B host, read, write, cache, asset, and lead tests show no cross-site access; unknown host is safe not-found |
| Publication safety | Only a published revision renders; invalid/draft content and unsupported visual variants cannot publish |
| Rollback/recovery | Intentional failure leaves no partial public state; clean recreation/restore achieves expected counts and isolation |
| Public visual parity | Existing Gym desktop/mobile baselines are compared for both Editorial and Classic using synthetic data; no real lead is submitted |
| Auditability | Run ID, command versions, fixture checksum, operator, results, and unresolved warnings are stored without secrets or PII |

## 8. Cost and risk boundaries

**Local-first estimate:** no provider spend is required beyond existing local
development prerequisites. Time, not cloud cost, is the main rehearsal cost.
Do not install a new database runtime or create a paid service under this
planning approval.

If a shared non-production environment is later justified, it may have a
recurring managed-database and hosting cost. That decision needs the provider,
owner, monthly budget limit, shutdown date, and explicit authorization. It
must not silently reuse or clone production.

Main risks and controls:

- **Accidental live connection:** use deny-by-default environment validation,
  loopback-only target allowlists, and tests that fail when a production-like
  URL or Apps Script host is configured.
- **Sensitive fixture data:** default to synthetic data; manual fixture review
  and secret/PII scan before sharing.
- **False confidence from a one-site test:** require two distinct sites and
  explicit cross-site attack cases.
- **Irreversible test state:** import only into disposable local/non-production
  databases and recreate instead of repairing ambiguous partial imports.
- **Migration drift:** version the schema, fixture, mapping, and import report;
  rerun the rehearsal whenever any of them changes.

## 9. Ordered implementation checklist (requires later approval)

- [ ] Choose the PostgreSQL provider and local runtime, named owner, and
  approved monthly ceiling for any non-local environment.
- [ ] Add schema migrations and an explicitly local seed/reset workflow.
- [ ] Create and review two synthetic Gym fixtures and their field mapping.
- [ ] Implement a dry-run-only importer and deterministic reconciliation report.
- [ ] Add a disposable import mode and prove idempotency.
- [ ] Add server-side local hostname resolution and site-scoped data access.
- [ ] Add a fake lead sink plus guards that reject Apps Script and production
  destinations in rehearsal mode.
- [ ] Add two-site isolation, cache, asset, invalid-publish, and rollback tests.
- [ ] Capture safe evidence and review every acceptance gate.
- [ ] Obtain a separate approval before creating any staging project, database,
  Vercel environment, cloud secret, deployment, or live Sheet backup.

## Decisions needed before implementation

1. Which managed PostgreSQL provider and local runtime will be used?
2. Is local-only rehearsal sufficient for v0.5.7, or is a separately approved
   shared staging environment required later?
3. Who is the named migration lead and who approves a dry-run/reconciliation
   report?
4. What monthly budget cap and automatic shutdown/review date apply if a
   non-production cloud environment is later created?
5. What exact synthetic fixture format will be the source of truth: a
   GymConfig-shaped JSON document, a Sheet-shaped key/value export, or both?
