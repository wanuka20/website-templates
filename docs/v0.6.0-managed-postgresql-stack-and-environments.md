# v0.6.0 Managed PostgreSQL Stack and Environment Decision

## Decision

Use **Neon Launch with PostgreSQL** for the future Gym pilot production
database. Use a disposable local PostgreSQL Docker runtime for development,
committed SQL migrations as the schema source of truth, and the existing
server-only `pg` package for application database access. Do not add a browser
database client or expose a database credential to the browser.

This decision selects the future live stack. A separate approval on 2026-08-02
authorized the synthetic-only Neon staging project and foundation restore
proof. It did **not** authorize a production project, billing subscription,
Vercel variable, public route, or customer-data connection. The completed
v0.5.7 rehearsal project remains separate historical evidence and was not
repurposed.

## Why Neon is the starting point

The Gym pilot needs ordinary PostgreSQL, a safe local workflow, a separately
operated staging environment, database backups, and PostgreSQL row-level
security (RLS) as defence in depth for the server-side `site_id` boundary.
Neon provides the managed PostgreSQL, pooled connections, autoscaling, and
branch/restore capability the pilot needs without committing the startup to a
fixed database plan before the traffic and data profile are proven.

Neon Launch is usage based. Its current pricing page uses roughly **USD
15/month** as an intermittent 1 GB example, with compute and storage charged
for usage. The initial synthetic staging project may use Neon Free while it
remains within its current limits; it is a separate project from production and
is never given production data. This gives the pilot a low starting cost while
keeping a clear path to paid staging if its test workload requires it. Set a
USD 75/month alert across Neon and any later storage/monitoring services, and
recheck provider pricing, resource limits, and restore retention immediately
before provisioning.

Neon is PostgreSQL only. The later upload task must select separate object
storage; that is an explicit future decision, not a reason to add an unused
platform service now.

RLS does not replace the planned server-only repository layer: table owners,
superusers, and roles with `BYPASSRLS` can bypass RLS. The application still
must derive `site_id` from the trusted request hostname and scope every query
and mutation to it.

## Comparison considered

| Option | Strengths for this project | Limitation for the Gym pilot | Decision |
| --- | --- | --- | --- |
| **Neon Launch / PostgreSQL** | Native PostgreSQL, usage-based compute, pooling, branching, restore tooling, and a low-cost fit for the pilot's small and variable workload | Object storage is a later separate decision; the Windows rehearsal runner needs an explicit IPv4 workaround that must be retested before live use | **Selected** |
| Supabase Pro / PostgreSQL | PostgreSQL, RLS, local tooling, backups, and future database/storage services under one operating model | Starts from a fixed USD 25/month plan before the pilot has demonstrated that its bundled services are needed | Not selected for the live pilot |
| Self-managed PostgreSQL | Maximum infrastructure control | Adds patching, backup, monitoring, recovery, and availability work before the two-site pilot has proved value | Rejected for the pilot |

The existing Neon rehearsal proved synthetic schema, fixture, isolation, and
restore steps only. Its local IPv4 workaround is a tooling constraint, not a
production design: validate the managed production connection independently
before enabling a live route.

## Environment model

Keep three isolated database environments. They are separate databases with
separate credentials and separate project identifiers; an environment name,
Git branch, hostname, or browser value is never sufficient proof of a target.

| Environment | Database and data | Permitted use | Prohibited use |
| --- | --- | --- | --- |
| **Local** | Disposable PostgreSQL Docker database, synthetic fixture/seed data only | Developer schema work, unit/integration/browser tests, migration dry runs | Production or customer data, production credentials, live lead delivery |
| **Staging** | Separate Neon project from production; synthetic or sanitised Gym data only for the pilot | Controlled migration rehearsal, integration tests, restore rehearsal, dedicated test hostnames | Production data, customer domains, Apps Script, Vercel production variables, real lead delivery |
| **Production** | Separate Neon Launch project; real customer data only after the later pilot gate | Approved public website reads/writes and approved production migrations | Seed commands, automatic database reset, automated test fixtures, development or preview access |

Production data includes copies from the production database, logical exports,
backups, customer images, lead contact data, and lead messages. It must never
be used by automated tests, local development, staging, preview branches, or
checked-in fixtures. The initial staging database is intentionally seeded from
the existing two synthetic Gym sites, not restored from production.

Neon branches may be considered later for short-lived pull-request checks, but
only when they are created from a safe staging/schema source and contain
synthetic data. A branch from production is forbidden because it includes the
source branch's data. Branches are not a substitute for the persistent staging
project, and temporary branches must be deleted or expire after the check.
Generic Vercel Preview deployments must default to no tenant data; a dedicated
approved test hostname is required before one can use staging.

## Delivery and access rules

1. Store schema changes as reviewed SQL migrations in the repository. A future
   guarded Node migration runner will use `pg` for the local, staging, and
   production targets; `pg` also remains the server-only application driver.
   No ORM is selected for this first foundation stage.
2. Apply and verify every migration in this order: **local -> staging ->
   production**. Production application needs a separate explicit approval and
   a backup/rollback check; it is never an incidental result of a local command.
3. Pass a named target explicitly. A remote migration command must display and
   verify the intended Neon project and branch identifier before any write.
   Destructive reset/reseed commands are limited to disposable local or staging
   targets and are permanently forbidden for production.
4. Keep one ignored local environment file per developer. Remote credentials
   live only in their matching Vercel/Neon environment scope or a protected
   CI secret store. Never copy, print, commit, or reuse a production connection
   string in local or staging.
5. Use separate migration, runtime, and maintenance roles. The public
   application uses a least-privilege server-only runtime role. Migration and
   backup roles are never used by application requests. RLS policies and
   `site_id` constraints remain required v0.6.0 security work.
6. Staging and production retain distinct backup/recovery records. A restore
   first goes into a separate non-production validation target; never restore
   over production as the first recovery action.

or connection string is stored here. Before creating the production project,
